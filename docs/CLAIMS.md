# Supported vs. Unsupported Claims

This document provides a transparent, empirical breakdown of claims that are supported by measured data in `jobmatch-eval` versus claims that are unsupported, misleading, or methodologically unproven.

Every claim is cross-referenced with exact files in `reports/` and documented experimental constraints.

---

## 1. Ingestion & Index Synchronization Claims

### Claim 1.1: Hash-based incremental synchronization delivers substantial speedup over full re-indexing for dense vectors.
- **Status**: **SUPPORTED BY EMPIRICAL EVIDENCE**
- **Empirical Evidence**:
  - In a simulated 9% mutation scenario (5% modified, 2% added, 2% deleted) across 3,000 postings, `sync_index.py` executed in **12.295 s** mean latency vs **159.636 s** for full scratch re-indexing (`reports/sync_benchmark.json`).
  - Effective throughput increased from 18.79 docs/sec to **244.0 docs/sec**, yielding a verified **12.98x speedup**.
  - State equivalence was 100% verified: identical document count (3,000), 100% ID set match, and exactly 0 content hash discrepancies.

### Claim 1.2: The entire job-matching retrieval pipeline updates incrementally.
- **Status**: **UNSUPPORTED / METHODOLOGICALLY INCORRECT**
- **Why**:
  - Incremental synchronization applies **only to the ChromaDB dense vector index**.
  - Lexical search relies on `rank_bm25.BM25Okapi`, which has no API for incremental document insertion or deletion.
  - Any dataset mutation requires rebuilding the BM25 inverted index and tokenized corpus in full (~5,992.1 ms startup cost, `reports/retrieval_latency.json`). The production architecture is hybrid: dense updates are incremental, while lexical updates require full rebuilds.

## 2. Retrieval Performance & Architecture Claims

### Claim 2.1: BM25 significantly outperforms Dense semantic retrieval in matching candidates to jobs.
- **Status**: **UNSUPPORTED AS A GENERAL RETRIEVAL CLAIM** (Supported only as retriever-rubric alignment)
- **Why**:
  - On the main evaluation benchmark, BM25 achieved an nDCG@10 of 0.6147 vs Dense 0.4231 (+0.1916 difference, 95% bootstrap CI [0.1109, 0.2610], `reports/retrieval_paired_comparisons.json`).
  - However, all evaluation labels in `data/eval/qrels.json` were generated by a deterministic rule-based heuristic rubric (`jobmatch-rubric-v1`) that scores candidate pairs using title-token overlap, location, and technical skill regex matching.
  - Because BM25 and the labeling rubric share lexical signals, BM25's higher score reflects signal circularity rather than superior real-world relevance for human job seekers.

### Claim 2.2: Cross-Encoder neural re-ranking yields superior ranking accuracy over Hybrid RRF.
- **Status**: **UNSUPPORTED / NOT DEMONSTRATED**
- **Why**:
  - Two-stage re-ranking using `cross-encoder/ms-marco-MiniLM-L-6-v2` over the top 50 Hybrid RRF candidates yielded an nDCG@10 of 0.5954 vs 0.6100 for Hybrid RRF (mean difference -0.0146, 95% bootstrap CI [-0.0579, 0.0308], `reports/retrieval_paired_comparisons.json`).
  - The confidence interval spans zero, demonstrating no statistically significant benefit over Hybrid RRF.
  - Furthermore, Cross-Encoder scoring added an average of 2,371.4 ms of CPU Transformer forward passes, increasing end-to-end query latency to **2,479.28 ms p50** (a 13.7x latency penalty compared to Hybrid RRF's 181.46 ms p50).

### Claim 2.3: Pure retrieval quality (without location or seniority filters) is rigorously benchmarked.
- **Status**: **UNSUPPORTED / NOT COMPARABLE**
- **Why**:
  - Candidate pooling was conducted in Phase 2A under active location and seniority filters to mirror product search constraints.
  - When filters were disabled in the "pure retrieval" setting, top-10 results had unjudged rates of **76.0% to 85.3%** across all strategies (`reports/retrieval_metrics_pure.json`).
  - Standard evaluation treats unjudged documents as non-relevant (label 0). As a result, out-of-market jobs retrieved when filters were off were penalized primarily because they lacked evaluation labels, rendering pure retrieval numbers invalid for comparing pure semantic vs lexical capability.

### Claim 2.4: Dense retrieval outperforms BM25 when queries have zero literal skill keyword overlap.
- **Status**: **INDICATIVE ONLY** (Sample size too small for conclusive proof)
- **Why**:
  - On the subset of 51 relevant candidate postings across 17 profiles that share zero literal keyword overlap with candidate skills, Dense retrieval achieved higher Recall@10 (0.3931 [0.23, 0.57] vs 0.2588 [0.12, 0.43]) and higher MRR (0.3437 [0.15, 0.53] vs 0.1751 [0.07, 0.31]) than BM25 (`reports/retrieval_circularity_check.json`).
  - However, exactly 13 of the 30 profiles had zero relevant documents in this slice and had to be excluded from Recall and MRR averages.
  - Because the sample size is only 51 pairs across 17 profiles, confidence intervals are wide, and this finding is indicative rather than statistically conclusive.

## 3. Dataset & Reference Label Claims

### Claim 3.1: The evaluation relevance labels constitute human-reviewed reference labels.
- **Status**: **UNSUPPORTED / FALSE**
- **Why**:
  - Zero human reviews were conducted (`human_reviewed: false`, `human_verified_count: 0`, `reports/label_agreement.json`).
  - All 1,037 labels in `data/eval/qrels.json` are rule-based proposed labels (`label_source: model_proposed`).
  - Inter-annotator agreement (Cohen's kappa, disagreement rate) cannot be computed and is withheld until a blinded human review is completed.

### Claim 3.2: The benchmark provides comprehensive coverage of all technical software engineering roles.
- **Status**: **UNSUPPORTED / DEMONSTRATED COVERAGE GAP**
- **Why**:
  - While mainstream roles (e.g. Junior Data Analyst with 32 relevant postings, Junior Software Developer with 21) are well represented, niche disciplines have severe coverage gaps in this 3,000-posting slice (`reports/relevant_docs_per_profile.json`).
  - Exactly 6 out of 30 profiles have fewer than 3 relevant documents:
    - `prof_07` (Mobile Developer, San Francisco): **0 relevant docs**
    - `prof_23` (Computer Vision Engineer, Remote): **0 relevant docs**
    - `prof_01` (Machine Learning Engineer, Remote): **1 relevant doc**
    - `prof_19` (NLP Engineer, Remote): **1 relevant doc**
    - `prof_09` (Database Administrator, Houston): **2 relevant docs**
    - `prof_11` (QA Automation Engineer, Denver): **2 relevant docs**

## 4. LLM Explanation Quality Claims

### Claim 4.1: Structured Pydantic validation ensures reliable JSON explanation schema compliance.
- **Status**: **SUPPORTED BY EMPIRICAL EVIDENCE**
- **Empirical Evidence**:
  - Across 150 explanation calls (30 profiles $\times$ top-5 BM25 matches) with `gemini-3.1-flash-lite`, the system achieved **100.00% first-try schema validity** (150/150 valid, 0 retries required, 0 fallbacks, `reports/llm_quality.json`).
  - Under the rule of three, 0 failures across 150 trials establishes a 95% failure upper bound of **$\le 2.00\%$** ($\le 3/150$).

### Claim 4.2: Claimed matched skills in LLM explanations are over 90% grounded in job posting text.
- **Status**: **SUPPORTED BY EMPIRICAL EVIDENCE**
- **Empirical Evidence**:
  - Standard boundary-safe regex groundedness is **91.70% pooled** (254/277 skills) and **91.79% macro-average** [0.88, 0.96].
  - When adjusted for 7 skills joined without whitespace in raw HTML postings (e.g. `JavaScriptUnderstanding`, `TableauExperience`), groundedness reaches **94.22% pooled** (261/277 skills) and **94.31% macro-average** [0.90, 0.98] (`reports/llm_quality.json`).
  - Truly ungrounded skills were limited to 16 occurrences (5.78%), primarily involving abstract conceptual leaps (e.g. `PowerBI`, `Strategic Planning`, `Budgeting`).

### Claim 4.3: High literal groundedness proves the LLM understands job posting context.
- **Status**: **UNSUPPORTED / CONCEPTUAL OVERREACH**
- **Why**:
  - Groundedness evaluation was performed strictly via programmatic regex matching against the job description text without an LLM or human judge.
  - A skill mentioned in an exclusionary clause (e.g., "Candidate will NOT be working with Docker or Kubernetes") would still be matched as literally grounded by regex.
  - Groundedness demonstrates lexical presence, not semantic or contextual comprehension.
